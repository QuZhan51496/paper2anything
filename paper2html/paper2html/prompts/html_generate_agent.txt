## Step 1 — Form a design concept BEFORE you write any HTML

First, read the manifest closely and decide (think it through internally; do NOT print this reasoning):
1. **What is this paper, really?** Its single most compelling hook — a benchmark with striking numbers? a method with an elegant mechanism? a surprising empirical finding? a new dataset? Identify the ONE thing a reader should remember.
2. **A visual concept / tone for THIS paper.** Choose a distinctive art direction that fits the subject matter — you decide it; do not pick from a fixed menu. Commit to a specific color story, typographic personality, spacing rhythm, and section-shape language. A GUI-agent paper, a translation-model paper, and a protein-folding paper should feel visually different.
3. **A narrative spine.** Decide the order in which ideas unfold so the page tells a story, not fills slots. Let the hook lead. Invent section names that fit this paper's vocabulary rather than generic labels like "Method" / "Results".
4. **Editorial choices.** What to enlarge, what to compress, what to omit. Not every paper needs every block. Compose unexpected but tasteful layouts (asymmetry, full-bleed moments, side-by-side comparisons, oversized numbers, pull quotes from the abstract) where they serve the content.

Then build the page to express that concept. Use the manifest's real material generously — the page should be substantial and have a clear visual rhythm with several distinct, well-crafted sections — but the set, order, naming, and styling of those sections is YOUR design decision for this paper, not a checklist.

You may of course use familiar ingredients when they fit (a hero with title/authors/links; oversized stat cards built from `claims`; a teaser figure; a method walkthrough; result tables; a gallery; a BibTeX block with a copy button; a footer) — but treat them as a vocabulary to compose with, never as a required sequence.

## Image & table presentation (use the `orientation`/`aspect`/`width`/`height` fields in the manifest)

Each figure and table screenshot carries `width`, `height`, `aspect` (=w/h), and `orientation` (`ultra-wide` / `wide` / `square` / `tall`). Use them so nothing is stretched or shrunk arbitrarily and sizes don't jump around:
- **NEVER** drop a bare `<img>`. Every image sits in a styled `<figure>` frame that matches your design concept (consistent corners, border/shadow treatment, inner background with padding, centered, `<figcaption>` in muted text). All frames on the page belong to ONE consistent family.
- Always `max-width: 100%`, `height: auto`, `object-fit: contain` — images never exceed the content column and are never upscaled past their natural size.
- Size by `orientation`:
  - `ultra-wide` (aspect ≥ 2.5, typically table/strip screenshots): full content-width banner; if still cramped, wrap the `<figure>` in a horizontally scrollable container (`overflow-x:auto`). Never stretch it tall.
  - `wide` (1.3–2.5): spans the content column or a wide card.
  - `square` (~1): 2-up or 3-up responsive grid at moderate size.
  - `tall` (aspect ≤ 0.8): center at a constrained, modest width — do NOT let a tall image dominate page height.
- The single teaser/hero figure may get a larger inspectable stage; optionally a self-contained click-to-enlarge.

## Table rules (respect `table_mode` = `{table_mode}`)

- **Strongly prefer rebuilding `tables[].html` as a real, natively-styled `<table>`** whenever HTML exists — a screenshot looks cheaper and breaks visual consistency. Style the native table to match your design concept: comfortable padding, a clear header, right-aligned numbers, and **bold the winning row/value** where context makes it clear. Add a one-line takeaway caption grounded only in that table's own numbers.
- `table_mode` semantics: `image` = use the screenshot; `html` = rebuild the HTML table; `auto` = prefer the screenshot only when no usable HTML exists, else rebuild HTML.
- A wide native `<table>` that overflows must sit in an `overflow-x:auto` wrapper, never squashed.
- Multiple result tables: lay them out clearly (stacked with headings, or tabbed).

## Hard constraints (validated automatically — violations are rejected)

1. **Images**: reference ONLY files in `figures[].file` and `tables[].image`, exactly as `images/<filename>`. Never invent/guess/alter a path. No placeholder images. Each image referenced AT MOST ONCE.
2. **Facts**: use ONLY the provided `title`, `authors`, `affiliations`, `abstract`, `claims`, `tables`, `method_components`, `bibtex`, `links`. Never invent numbers, results, authors, affiliations, or claims. Omit a section if its material is missing — never fabricate filler.
3. **Links**: resource buttons use ONLY non-empty `links` URLs. Never output a bare `href="#"` (in-page anchors like `href="#results"` are fine).
4. **Self-contained**: ALL CSS and JS inlined. The ONLY permitted external resources are the MathJax CDN (`https://cdn.jsdelivr.net/npm/mathjax@3/es5/tex-mml-chtml.js`) and local `images/`. No Tailwind CDN, no Google Fonts, no external CSS/JS, no icon CDNs. Use a system-ui/Inter-stack font in local CSS; inline SVG or unicode for icons.
5. **Math**: include the MathJax CDN script; use `\( \)` / `\[ \]` sparingly.
6. **Output format**: return the COMPLETE HTML document ONLY, starting with `<!DOCTYPE html>` and ending with `</html>`. No markdown fences, no commentary, no design notes — just the page.
